Methodology

Every number this application reports is defined here, and every parameter behind it is on this page. Nothing is hard-coded: thresholds, weights and lexicons all come from packs/ and are edited by the Working Group.

Principles

  1. Four axes, not one number. Capability, safety, bias and grounding measure different things. Any composite is a convenience figure, shown only with its weights.
  2. No score without its denominator. Every figure carries n, its interval and the suite version that produced it.
  3. Parse failures are reported, not absorbed. An unparseable response is its own category; counting it as wrong would charge a harness limitation to the model.
  4. Judges are part of the measurement. Where a judge scores a response, its identity and version appear beside the score.
  5. Scoring is re-runnable. Responses are stored, so changing a threshold re-scores existing evidence without re-querying any model.

Answer extraction

Multiple-choice answers are extracted deterministically, in this order: explicit letter (A–D); explicit index (0–3); exact restatement of one choice. Anything else is unparseable — reported as its own category, never scored as wrong.

Where a judge is used, its agreement with a human-labelled calibration set is measured each time the judge model or judge prompt changes. Below the minimum κ, that judge may not be used for a scored run. A cloud judge reading restricted on-prem content would breach data residency, so restricted suites must use an on-prem judge.

Comparability

Two results are comparable only when suite major version, dataset revision, scorer version, judge configuration and sampling parameters all match. Every run records all five in its run settings. A sampled run is labelled sample throughout and is not comparable to a full run.

Ownership and governance

How the Working Group edits the tests

Every test, probe, threshold and pass/fail criterion lives in packs/ as YAML under version control. Nothing there is code.

  1. Change the YAML in packs/.
  2. Run python3 -m harness validate — it names the file, the path inside it and what is wrong.
  3. Bump the suite version (major if comparability of scores changes) and add a changelog entry.
  4. Open a pull request. Working Group review is the approval gate.

The test suites themselves, with their basis, tests, readiness and results, are under Test suites in the sidebar.
